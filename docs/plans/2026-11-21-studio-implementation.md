## 每个模块的完成条件

1. 读取该模块列出的材料，确认依赖模块的远端提交及验收证据。正式开发以 `master` 为基线，只在 `develop` 分支提交功能，后续由项目负责人合并回 `master`。按顺序实施，外部材料缺失时记录受影响的场景，继续验证无需该材料的部分。
2. 按模块检查点运行验证，保留命令和结果。在 `docs/验收/` 按模块编号记录对应 AC、环境、样本、预期与实测、证据位置，以及尚待最终集成的场景。付费和生产链路保存脱敏的请求及执行 ID、文件规格、规则版本、审核决定与费用记录。模拟验证和真实服务验证分别记录。
3. 【提交】检查 `git status --short` 和 `git diff --check`。仅暂存本模块的代码、迁移、测试和验收记录，复核 `git diff --cached --check` 与 `git diff --cached --stat`，按模块的建议消息做一次提交。
4. 【推送】模块 00 在已有 `master` 初始提交后创建 `develop`：`git switch master && git pull --ff-only && git switch -c develop && git push -u <remote> develop`。后续功能只推送 `develop`，使用 `git push <remote> develop`。用 `git merge-base --is-ancestor <module_commit> <remote>/develop` 核对模块提交已在远端历史中，不要求远端当前 HEAD 恰好等于本地提交。若远端拒绝或校验不一致，保留本地提交，处理冲突或访问问题后重推，禁止强推和覆盖他人变更。
5. 验证通过、提交存在、远端 SHA 匹配后，在执行记录中勾选模块并汇报测试结论、分支和提交 SHA。模块 17 汇总此前的实际提交与证据。跨模块 AC 在本模块只记录已经通过的子场景，最终完整验收统一由模块 17 判定。

模块 01 建立并在开发指南固定实际命令。建议前端提供 `pnpm --dir apps/web lint`、`typecheck`、`test`、`build`、`test:e2e` 对应脚本，后端提供 `uv run --project apps/server ruff check apps/server`、`uv run --project apps/server pytest apps/server/tests` 和 Alembic 迁移烟测入口。后续模块用这些入口按功能过滤测试，再跑受影响的集成回归。
